## 4. 第三階段：參考計價（FDS-08）

### 4.1 使用流程與規則

- 唯一產品入口為「報價預算 → 參考報價」，不新增獨立「套餐計價」選單，也不改現有 pitching 快速報價。
- 使用者先選 PMS 項目，再**自行選定一張 QMS 報價**，讀其傢俬 Section／明細。
- 名稱與單位正規化後完全一致，且只有一個候選時才可自動匹配 2026 價目。重名、多候選、缺少資訊或未匹配時由使用者手動選擇；不可用模糊猜測靜默定價。未完成匹配不可整批導入。
- 保留來源項目、報價、Section、明細識別及原始文字，方便追溯；不回寫 QMS／PMS 報價。
- 2026 既有程式規則為小計＝數量 × 平均價，按分區合計；標準／高品質區間只作參考，不計入總額。既有程式記錄該年度表沒有運輸／安裝加成。須對照實際工作表再確認；發現與舊 PRD「各套餐計價」說法衝突時記錄差異並確認，不自行新增比例或採 AI 價格。
- 工作表：<https://docs.google.com/spreadsheets/d/1dsHI6pd8UcynkddFw01heLFpaNAWevkf2YH1mT35edU/edit?gid=664577347#gid=664577347>。無法取得時明確列為外部資料待核對，不聲稱已完成公式驗證。
- 數量 0 的小計為 0；非法數字與負值不可形成有效報價。貨幣金額以仙處理，畫面、分區小計、總額、保存快照及 PDF 一致。
- 管理員維護基準價。已保存報價保存當時價格快照；改基準價只影響之後新單。不得重開舊單時重新套最新價。
- 參考 PDF 含標題、分區、項目、規格／單位、數量、單價、小計、總額及參考報價聲明；已有該單客戶分享連結才顯示其 QR。

## 10. 第四階段：BWF 分區示範圖與場景（FDS-13，P2）

### 10.1 範圍與流程

只在「報價單一覽」的 BWF 正式報價 `bwf_quote` 提供。排除有設計專案殼、`DP-` 單號、快速報價及客戶方案；設計專案、參考計價與客戶授權頁沒有生成按鈕。伺服器也必須檢查範圍與角色，不能只隱藏前端。

流程：上傳 PDF／JPG／PNG 平面圖 → 識別圖上已有區域名稱和矩形 → 使用者調整或手畫並確認 → 在該報價分區選產品圖 → 生成一張透視示範圖 → 可選擇從該圖生成一個 GLB 場景 → 預覽 → 人工確認才掛入分區。

### 10.2 資料及生成規則

- 沿用正式報價分區標題與其後明細。範圍綁定分區 ID，存在該報價 `project_data`；不新增區域表、不讀 `project_zones`。
- PDF 先用現有渲染能力取得預覽；矩形用相對預覽圖百分比，必須在圖內。最多 24 區，不發明圖上沒有的房間；座標失效時保留名稱供手畫，完全無法識別時可手動新增。
- 更換平面圖後範圍需重新確認；名稱與既有分區圖片保留。刪分區移除其範圍。上傳／換圖與背景載入並行時不能清掉明細。
- 權限沿用現有參考圖生成：admin、uploader、PM；第一版不開放 designer。
- 每次輸入 1 張該區截圖＋最多 10 張使用者勾選的產品圖，及該區傢俬名稱、數量、顏色、已有尺寸。缺圖產品不佔圖片名額；沒有傢俬仍可只用截圖。
- 沿用既有參考圖生成服務及實際 slug，固定 Gemini；一般圖片庫仍維持最多 5 張參考圖，不跟著放寬。生成 4:3 室內平視透視圖，不加文字或商標，盡量保留產品外觀與顏色。
- 圖片先預覽，確認才追加；每分區沿用上限 8 張，已滿拒絕追加。失敗保留範圍和選擇，可重試。取消不掛入分區，既有圖片庫可能仍保留生成圖。
- 圖片及場景標示「僅供設計參考，示意搭配，不可作施工圖」，不承諾尺寸、比例或型號準確。

### 10.3 GLB 場景

- 先盤點並選定現有「單張透視圖 → 一個 GLB」能力；若沒有適用供應商，列為待決策，不默認選用 Tripo 或新建建模軟件。
- 只使用剛生成的透視圖產生整區一個場景，不做逐件家具編輯。沿用現有 GLB 視窗旋轉、平移、縮放。
- 檔案放既有私有儲存，存取跟報價平面圖一致；`project_data` 保存分區、透視圖及場景關聯，不新建場景表或公開入口。
- 人工確認才掛入分區；場景失敗仍可單獨確認透視圖。取消不掛入。重生成透視圖、更換平面圖需重新確認或刪分區後，舊場景不可再用。
- 場景不進對外 PPT 或客戶授權頁，不提供場景 SKP／FBX；單件模型仍屬 FDS-06。

驗收：合法範圍與角色、舊單相容、換圖失效、缺圖／超限／生成失敗、保存及取消、並行載入不丟明細；桌面可查看場景，手機可完成選區、確認和透視圖生成。

- 固定三段且不可刪除：報價內容簡述、可電話聯繫（取該報價負責同事已有電話）、該報價加單授權連結。可附加自訂內容。
- 發信身份由環境設定的系統信箱取得，不在前端寫死。沿用已存在的發信服務、紀錄與 PM 資料來源，不新建通訊錄。
- 發送前驗證收件人、負責人聯繫資料、有效分享連結；缺資料顯示可處理的錯誤，不猜測地址或電話。

### 12.2 自動跟進與查看事件

- 手動與自動使用該單當下模板；自動跟進每 3 天一次。同單不可重複建立排程，並行 worker 不可重複發信。
- 客戶首次有效打開該報價授權頁後，只停止該單自動信。其他報價不受影響。選品／加單提交另外通知 PM。
- 客戶由郵件加單連結成功載入授權頁，保存報價、查看時間及對應發信紀錄，並通知 PM；重複事件需去重。
- 郵件圖片預載、連結安全掃描及機器人 HTTP 請求不算有效查看。不能在分享連結 GET 或追蹤圖片載入時直接停信。實作需明確記錄有效查看判定、授權驗證、已知掃描排除及無法可靠辨識的限制；對會執行 JS 的掃描器不能保證零誤判，需在驗收前確認策略。
- 沿用業務狀態 Not Sent、Sent、Auto Follow-up Active、Viewed、Stopped。發送、重試、查看與停信須可追溯，排程發送前再次檢查是否已查看或停止。

驗收：A／B 模板隔離、三固定段完整、手動發送、三天邊界、模板更新、並行重試去重、有效查看後停止、掃描不通知、停信與發送競爭，以及 PM 通知失敗可恢復。驗收優先使用測試信箱／郵件沙盒；沒有明確發送授權不向真實客戶發送。

## 13. 共用實作約束

- UI 沿用 `src/components/ui`：Modal（全頁用 fullscreen）、Switch、Select、Checkbox；確認用 `@/components/ui/confirm-dialog` 的 `confirm()`，不使用原生 alert／prompt／confirm 或手寫對話框。
- 產品列表使用輕量欄位，不 `.select('*')`；重量圖片只單筆懶載入。圖片先上 Storage 再存 URL，不將 base64 寫入資料庫。
- 正式報價沿用 `bwf_quote`／`bwf_quote_item` 及 `save_bwf_quote_items`；不把明細重新塞回 `project_data.items`。參考報價快照不改正式報價金額。
- DB 變更向後相容，先查既有 RLS、RPC、儲存與角色契約，伺服器重新驗證權限。不能只用前端判斷隔離。
- 修改 Edge Function 前找出前端實際 invoke slug；部署時用該 slug，並抓回線上封裝確認版本。共享模組要一起打包，單檔上傳不足以證明部署正確。
- 顯示真實進度、空狀態及可重試錯誤，不用靜態資料假裝完成整合；產品文案避免內部表名、service role 等實作細節。

## 14. 執行次序與交付定義

1. 建立逐項現況表：已有實作、可重現缺陷、待驗收、外部依賴。先驗證參考報價，再處理圖冊附件、單件模型、分區及案例。
2. 先交付第三階段可獨立驗收的修復；Asana 權限準備與其他工作分開，不作整階段的全域阻塞。
3. 第四階段先核對共用報價／授權／通知契約，再實作客戶提交與郵件狀態；分區場景供應商未選定時，可先完成透視圖及確認流程，但不得把整項標完成。
4. 每個改動附對應檢查；執行適用既有測試、`npm run build`、`npm run audit:ui`。重要計價、快照隔離、token 範圍、同步／發信冪等及非同步競爭需有回歸測試。
5. 更新本文件的交付狀態或另寫驗收紀錄，提供環境、commit／工作區版本、樣本類型、結果與限制；不在文件寫客戶隱私或憑證。
6. 分開報告「本地完成」「測試通過」「migration 已套」「function 已部署」「前端已發布」「真實流程已驗收」。只有相關驗收全部通過才勾選該功能完成。

本次文件交付不授權自動 commit、push、Production migration、Production 部署或真實對外發送；先完成可審閱修改與測試，再按使用者後續授權執行。
